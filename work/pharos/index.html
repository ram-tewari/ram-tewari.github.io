Pass 1 · Overview

What problem does PHAROS solve?

PHAROS gives an AI coding assistant real code it can cite, and proves which version of the code that is before handing it over.

Why it matters. An assistant reading a codebase gets whatever retrieval hands it. A stale chunk looks exactly like a current one, and a confident answer hides which is which. Most code search asks “what looks relevant?”. I built PHAROS around a stricter question: “what can be shown to be true at this commit?”.

  • Measured: held-out nDCG@10 rose from 0.394 to 0.697 and from 0.463 to 0.726 on two locked sets of 101 questions, with a single annotator.
  • Failed: repository memory missed its primary gate. It is shown below at the same size as the win.

Pass 1 · Overview

What did Ram build, and what changed?

My contribution

What I built
PHAROS itself, in Python and FastAPI: a Tree-sitter indexer for symbols, imports and calls; keyword and dense retrieval fused by rank, with mode routing (the audited auto mode chooses dense, hybrid or keyword; the SPLADE sparse retriever from its earlier search module is implemented, but auto does not route to the sparse retriever); verification of every cited source against its commit; and the REST and native MCP interfaces assistants call. Indexing and embedding run in asynchronous workers, apart from the API.
The tradeoff I chose
Provable over plentiful. When PHAROS can’t verify something, it returns less: a retrieval mode it can’t run fails out loud instead of quietly substituting another, a citation is checked against its Git blob before it is returned, and an ambiguous call stays unlinked rather than guessed. On its own code that leaves about three quarters of calls unlinked. I accepted that cost.
What changed
Held-out nDCG@10 rose from 0.394 to 0.697 and from 0.463 to 0.726 on two locked sets of 101 questionsreported · one annotator. Assistants get code they can cite to a commit, path and line span. And when repository memory missed the gates I set for it before writing it, the miss went on this page, not into a footnote.

Pass 2 · How it works

What’s the idea, in one picture?

Picture a librarian who files every page by the edition it came from, finds pages by meaning or by name, and checks the edition stamp before handing one over. If the stamp doesn’t match, you get nothing, not the wrong page.

  1. 01File it

    Code is cut along its own structure, into functions and classes, and filed under the commit it came from.

  2. 02Keep pointers

    The database keeps where code is, its vectors and who calls whom. The code itself stays in Git.

  3. 03Find, then check

    A question is answered by meaning, by name or both. Then each file is re-read at its commit and its fingerprint compared.

  4. 04Hand it over

    An assistant gets cited code through the same tool calls it uses for anything else.

For engineersOpen detail
  • A bare shallow clone is read with git cat-file at a pinned commit, so symlinks and submodules cannot escape the repository, and repository code is parsed, never run.
  • Remote repositories must be https on an allowlisted host. Local paths can only be registered through the CLI, so API callers cannot reach the worker's filesystem.
  • Jobs live in PostgreSQL with atomic claims and retries. Read the claim.
  • Files are compared by Git blob SHA. Unchanged files only move their commit pointer. Read the diff.
  • The last commit is written after everything else, so a failed run leaves the previous index searchable. Read the run.

        How did it get here?

        PHAROS didn’t start as a code-search service. It started as a much bigger idea, and most of what it is now came from finding out which parts were real.

        1. Sep–Dec 2025

          It began as Neo Alexandria

          A research library: papers, citations, annotations, recommendations, and three-way search fused by rank, planned phase by phase as requirements, design and task documents. The SPLADE retriever comes from here.

          What it taught me A plan for every phase is not proof for every phase. Its own test-fix specification recorded 74.8% of tests passing.

        2. Jan 2026

          Tests an assistant can’t rewrite

          Expected values moved into read-only golden-data files, and a failing test says not to edit the test.

          What it taught me Write the answer down before the code can see it.

        3. Feb–Apr 2026

          Renamed PHAROS, and pointed at code

          A cloud API with a separate GPU worker, AST parsing and code search, aimed at coding assistants.

          What it taught me A narrower question is easier to answer well.

        4. Apr–May 2026

          Audit the claims, including mine

          An April audit, run by an AI reviewer told to trust no documentation, found 3 of 9 components missing, stubbed or invented. A May review found search returning results with no file paths and no code.

          What it taught me Documentation is a claim, and claims need evidence.

        5. Jul 2026

          Cut back to the core

          The knowledge-management product was removed, module boundaries became a CI gate, and PHAROS began speaking real MCP.

          What it taught me Removing a feature can be the most useful change.

        6. Oct–Nov 2026

          Rebuilt around proof

          A chunk-level code index with verification at commit. Labels were hashed before any run, each locked test set was run once, and the memory protocol was fixed before memory code existed. Retrieval passed; memory failed, and the failure stays on this page.

          What it taught me Set the bar first, then publish whichever side of it you land on.
