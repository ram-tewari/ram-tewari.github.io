How I work

Creative about the question.
Methodical about the proof.

I treat engineering as a creative discipline with a strict method. The creative part is finding a better question than the one I was handed. The methodical part is deciding what would prove the answer before I build it, then keeping the result, including the parts that fail.

  1. 01 Creative

    Reframe the problem

    Start from a better question than the one on the ticket.

    • PHAROS Code search for AI assistants, reframed as an evidence problem: every answer should name the commit it came from.
    • R&Bot Lyrics, reframed as structure: section tokens so the model writes a song a verse, chorus and bridge at a time.

  2. 02 Methodical

    Decide what would prove it

    Write the bar down before building, so the result can’t move it.

    • Ultraviolette Code, not the language model, decided whether a product claim was correct: a deterministic verifier with numeric tolerances.
    • Valerie A model may propose one typed move. Fixed rules decide whether it runs, and the model can’t change them.

  3. 03 Creative

    Make it something you can touch

    Build the smallest version a person can actually try.

    • Magna A teleoperation interface operators drove by keyboard and joystick, with command latency measured at 58 and 62 ms.
    • This site A building you can walk. Four of PHAROS’s machines run its real code in your browser, and Valerie’s boundary takes your attacks.

  4. 04 Methodical

    Measure, and keep what fails

    Report the result against the bar, and publish the misses beside the wins.

    • PHAROS Test sets and memory gates were locked before the final runs. Retrieval rose; memory failed its gates, and stays on the page at the same size.
    • Ultraviolette In a 40-session A/B test, retrieval cut prompt tokens 24%, and the test also checked that all 11 planted factual errors were still caught.
